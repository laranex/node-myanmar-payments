# Changelog

All notable changes to `@laranex/myanmar-payments` (node-myanmar-payments) will be documented in this file.

## v4.0.0 - Unreleased

Initial release. The version number matches the other Laranex Myanmar payments packages (`php-myanmar-payments`, `laravel-myanmar-payments`, `go-myanmar-payments`, `python-myanmar-payments`), and the gateways, flows, validation, signing, status maps, results and errors are a port of them, sharing their test vectors.

### Added
- Gateways: KBZ Pay (`pwa`, `qr`, `app`, `status`), Wave Pay (`initiate`), Wave Pay Mini App (`accessToken`, `forgetToken`, `payment`), AYA Payment Gateway (`services`, `initiate`, `status`, `verifyRedirect`), Yoma MMQR (`initiate`, `renewQr`, `status`, `forgetToken`) and CyberSource Secure Acceptance (`initiate`); every gateway validates its payment data (`KbzPay.validate()` and so on) and verifies callbacks with `handleCallback` (Wave Pay Mini App's also takes the callback URL).
- Subpath exports per gateway (`@laranex/myanmar-payments/kbz-pay`, `/wave-pay`, `/wave-pay-mini-app`, `/aya-pay`, `/yoma-mmqr`, `/cyber-source`) next to the root export, as ES modules and CommonJS with type declarations.
- Exact `Amount` type (`Amount.kyat()`, `Amount.parse()`) kept as decimal text, so amounts never pass through a float; payment data also takes a whole-number `number` or `bigint` and rejects fractions. Decimals are accepted only where the gateway documents them (KBZ Pay up to 2 places, CyberSource any); every gateway except CyberSource is MMK only.
- A config class per gateway with `fromEnv(process.env)`, reading the same credential, setting and URL variables as the PHP, Laravel, Go and Python packages; a missing setting throws `ConfigurationError`. `optionsFromEnv(env)` on every config class returns the options `fromEnv()` reads without validating them (unset or blank variables left out), so a framework can merge its own options with the environment per key. `MyanmarPayments` builds every gateway lazily from one config object or the environment.
- Wave Pay follows the Pay with Wave API spec v1.3: payments are a JSON post to `baseUrl`'s `/payment` (Content-Type and Accept `application/json`) with `amount` and `time_to_live_in_seconds` as JSON integers, `currency` `MMK` and `items` as a JSON string array, and the customer is sent to `baseRedirectUrl`'s `/authenticate` (UAT: `https://preprodpayments.wavemoney.io:8107` for both; production: `https://payments.wavemoney.io`). `WavePayPaymentData` takes optional `additionalField3`, `additionalField4` and `additionalField5` (at most 50 characters each, sent as `additional_field_3` to `additional_field_5` only when non-empty) and enforces the spec's limits: `orderId` and `merchantReferenceId` at most 100 characters, `callbackUrl`, `returnUrl` and `description` at most 255 (counted in UTF-8 bytes). Amounts are sent with every digit and, without `amount` (unset or `null`), the total is the exact sum of the items; item names and amounts and the total are checked after the other fields; no items and no `amount` reports `The amount field is required.`, and an item amount that is invalid or has decimals skips the total check. A failed request's message lists `errors` only when it is a JSON object, and `gatewayCode` is `VALIDATION_ERROR` whenever `errors` is present, even null.
- Wave Pay Mini App follows the Wave Money JS SDK spec v1.8 for a web page running inside the WavePay app: `accessToken({ signal })` posts `client_id`, `client_secret` and `grant_type=client_credentials` as a form to `baseUrl`'s `/auth/v1/external-utility/token` and caches the token like Yoma MMQR's (`myanmar-payments.wave-pay-mini-app.token.<sha256 of base URL|client id>`, `expires_in` minus a minute; `forgetToken()` drops it), for the page's `WaveJsSDK.authModule.loginWithAccessToken()`. `payment()` sends no request: it returns a `MiniAppPayment` whose `toJSON()` is exactly the `makePayment` object (`amount`, `miniAppID`, `merchantRefID`, `orderID`, `callBackUrl`, `hashValue`, `items`; amounts as JSON numbers) and whose `toJsonString()` writes amounts as JSON integers with every digit, hashed with HMAC-SHA256 over `amount . orderID . miniAppID . merchantRefID . callBackUrl`. Amounts are whole kyat, the total defaults to the exact sum of the items, and `merchantReferenceId` is generated (32 hex characters) when empty. `handleCallback(request, callbackUrl)` verifies the same hash with the callback URL the payment was signed with (the callback carries neither it nor the mini app id), then requires a non-empty `orderId` and `merchantRefId` and a whole-number `amount` (`Wave Pay Mini App callback is malformed.`); `successful` is successful, `processing` pending and `failed` failed. UAT: `https://preprodnewapi.wavemoney.io`; production: `https://api.wavemoney.io:8100` (`WavePayMiniAppConfig.PRODUCTION_URL`).
- Wave Pay callback statuses per the spec: `PAYMENT_CONFIRMED` is successful; `BILL_COLLECTION_FAILED`, `INSUFFICIENT_BALANCE` and `ACCOUNT_LOCKED` are failed; `SCHEDULER_TRANSACTION_TIMED_OUT` (and `TRANSACTION_TIMED_OUT`) is expired; `PAYMENT_REQUEST_CANCELLED` is canceled.
- Configuration: every setting of a gateway you use is required and has no default, except the HTTP timeout (`timeoutSeconds`, `MYANMAR_PAYMENTS_HTTP_TIMEOUT`), which defaults to `DEFAULT_TIMEOUT_SECONDS` (30). That includes the URLs (`PRODUCTION_*` constants on the config classes name production's), the time to live (KBZ Pay's `timeToLiveMinutes`, `KBZ_PAY_TIME_TO_LIVE_IN_MINUTES`, 1 to 120; Wave Pay's `timeToLiveSeconds`, `WAVE_PAY_TIME_TO_LIVE_IN_SECONDS`, greater than 0; time settings take a whole number or its text), Yoma MMQR's `webhookSecret` (`YOMA_MMQR_WEBHOOK_SECRET`, checked on every callback's `X-Webhook-Secret`), Wave Pay's `merchantName` and Yoma MMQR's `apiVersion`. A missing or blank setting throws the `ConfigurationError` naming it; a value out of range throws one such as `The kbz_pay configuration [time_to_live_in_minutes] must be a whole number from 1 to 120.` Whole-number settings hold at most 2147483647. Text settings also take a safe integer (`merchantCode: 200123` becomes `'200123'`); floats and booleans count as missing. Settings are checked in a fixed order: the required strings, then the time to live, then the timeout. Only ASCII whitespace and NUL are trimmed from settings, statuses and bodies (a no-break space or byte order mark is kept), like PHP `trim()`.
- Time to live per payment: `KbzPayPaymentData`'s `timeToLiveMinutes` (1 to 120) and `WavePayPaymentData`'s `timeToLiveSeconds` override the configured value. `WavePayPaymentData` also takes an optional `merchantName`. CyberSource payments take `currency`, `locale` and `transactionType`.
- Result classes: `RedirectPayment`, `FormPayment` (with `toHtml()`), `QrPayment` (with `qrImageDataUri()`), `AppPayment` and `MiniAppPayment` (with `toJsonString()`); `PaymentCallback` (with a gateway-independent `PaymentStatus` and the `Acknowledgement` each gateway expects, sent with `send(res)` or `toResponse()`) and `PaymentStatusResult`.
- `CallbackRequest.fromNodeRequest()` (node:http, Express), `CallbackRequest.fromWebRequest()` (Fetch API servers such as Next.js, Hono and Bun), `CallbackRequest.from()` and `CallbackRequest.fromJson()`. JSON numbers in callbacks are read without a float conversion, so signatures and amounts keep the gateway's exact text.
- `CallbackRequest.rawBody` holds the exact bytes received, next to `body` as text. JSON numbers stay exact strings in `raw`, `parsedBody()`, `input()` and `queryInput()` (`1000.50` is `'1000.50'`).
- `Amount.equals()` compares by value, ignoring leading zeros (`'01000'` equals `Amount.kyat(1000)`).
- Errors: `PaymentError` and its subclasses `InvalidPaymentDataError` (per-field `errors`), `ApiError` (`gatewayCode`, `gatewayMessage`, `httpStatus`, `raw`, `cause`), `SignatureVerificationError` and `ConfigurationError`.
- No runtime dependencies: the global `fetch` (or an injected `fetch` / `HttpClient`, the configured `timeoutSeconds`, `AbortSignal` per call) and `node:crypto`; an injectable `TokenCache` with an in-memory default for the Yoma MMQR and Wave Pay Mini App access tokens.
- CyberSource callbacks trust only the fields listed in `signed_field_names`: `decision` and `req_reference_number` must be signed, and unsigned fields are left out of the result and `raw`.
- Callback hardening: AYA Pay payloads need their order, transaction, amount, currency (104) and status fields well formed and no `:` in a signed value but `dateTime` (and payments reject `:` in `orderId`, `description` and `userRefs`); CyberSource rejects a `signed_field_names` that does not sign itself, repeats or empties a name, and any `decision` outside ACCEPT, REVIEW, DECLINE, ERROR and CANCEL; Wave Pay needs a decimal `amount` and ids of letters, digits, `_` and `-` (also enforced on payments). A bad signature, hash or checksum throws `... verification failed.`; a check that fails after it matched throws `Wave Pay callback is malformed.`, `AYA Pay {callback|redirect|enquiry response} payload is malformed.` or `CyberSource callback is malformed.` (CyberSource's unsigned `decision` / `req_reference_number` and unknown decision included); `fromNodeRequest` and `fromWebRequest` read at most 64 KiB (`maxBodyBytes`); `FormPayment.toHtml(nonce)` adds a CSP nonce.
- AYA Pay reads a `payload` whose `+` signs became spaces in an unencoded return query string. `services()` reads `data` and each service's `methods` only as JSON lists and skips method entries that are not scalars. Payments reject `:` in `orderId`, `description` and `userRefs` with `The {field} field must not contain ":".`
- A negative whole-number amount is reported with the other invalid fields as `The amount field must not be negative.` (`items.<i>.amount` for a Wave Pay item).
- Redirects are never followed: the default client calls `fetch` with `redirect: 'manual'`, so a 3xx response is handled like any other non-2xx one.
- Callback, return and cancel URLs only need to be valid absolute http or https URLs (PHP's `FILTER_VALIDATE_URL` rules: printable ASCII, an ASCII host name of labels up to 63 characters or a bracketed IPv6 address, a port up to 65535); there is no HTTPS-only rule (gateways may still require HTTPS in production).
- Behavior is identical to the PHP, Go and Python SDKs, checked by shared vectors: signing (a nested value in a signed field fails verification), AYA's base64 rules, the Yoma MMQR and Wave Pay Mini App token cache keys (`myanmar-payments.yoma-mmqr.token.<sha256 of base URL and client id>`), the Wave Pay Mini App token request and payment payload, `FormPayment.toHtml()`, URL validation, query escaping, whitespace trimming, configuration and validation order, response reads and every error message.
- Agent skill in `skills/node-myanmar-payments` so coding agents use the package correctly; install it with `npx skills add laranex/node-myanmar-payments`.
- Requires Node.js 20 or higher.
